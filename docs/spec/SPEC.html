1. Introduction

1.1 Purpose

This document says what the first version of Tenure must do (§3) and how well (§4). It is the working document for the people and agents who build, test and review that version, and for Uzair, who approves its scope.

Tenure helps independent gyms keep new members past their first 90 days. It counts each new member's visits week by week, shows who is slipping, and lets a coach nudge them with a message sent from the coach's own phone.

1.2 Scope

The first version is the whole MVP, built simply: every core screen, the account basics, and a simple public website with sign-up. Its core flows are tested end to end, through the server and in the browser, and small rough edges are allowed. It runs on one machine, locally or in Docker. In stall mode it serves phones and the kiosk on that machine's local network (FR-OPS-01).

2. Overall description

2.1 Product perspective

Tenure is a self-contained web app on one machine. In stall mode and in Docker, one server, the API on Node 26, serves the website, the app and the kiosk, answers their JSON requests, and streams live events to open screens (FR-LIVE-01). All data lives in one SQLite file on the same machine (FR-PRIV-01). At the stall that machine is a Mac, running Tenure in Docker or with npm run stall, and phones and the kiosk tablet reach it over the laptop's local network (FR-OPS-01).

The browser app is one React app: the website, the app under /app, the kiosk, and the invite and reset pages. The website loads without the app's code (FR-WEB-05).

Tenure contacts no outside service (NFR-PRIV-01):

  • A nudge opens the coach's own Messages or WhatsApp with the message filled in, and the coach sends it (FR-NUDGE-02, FR-NUDGE-05).
  • Email, texts and payments go through stand-in adapters (FR-DEV-02). Email goes to the outbox table. Nothing in the first version sends a text or takes a payment (FR-NUDGE-05, FR-BILL-01).

The first version replaces the old expo app, kept in legacy/app as the reference for the port. Its flows and rules carry over into the new layout (ARCHITECTURE §3), changed where answers.md and the first-version plan say so.

2.6 Assumptions and dependencies

Assumptions

  • The laptop's clock and time zone are right on the day. The demo gym's dates are relative to the day it was seeded, in the laptop's zone, so it is re-seeded on the morning of the stall (FR-GLOBAL-05, ARCHITECTURE §12).
  • The operator re-seeds the demo between visitors (FR-OPS-03). Until then, a visitor who taps "Try the demo" sees what earlier visitors entered at the kiosk, names and phones included, as any owner would (FR-WEB-04).
  • The laptop's firewall lets phones and the kiosk connect on port 5175.
  • Coaches send nudges from their own phone or computer, with Messages or WhatsApp set up on it. A text needs mobile service, and WhatsApp needs the internet (FR-NUDGE-05).
  • Each gym is in one of the five markets (FR-GLOBAL-01). Its members' phones are local numbers, or typed with "+" (FR-GLOBAL-02). The demo keeps its +1 sample numbers in every country (FR-GLOBAL-05).
  • A gym's existing members come in as a CSV file of up to 2 MB, or as pasted text (FR-IMPORT-01).
  • No email leaves the machine. Staff take invite links by copying them (FR-STAFF-03), and reset links from the operator (FR-AUTH-08).
  • Backups are the operator's to keep. A deleted member stays in older backups (NFR-PRIV-02).

An API module is a folder, apps/api/src/modules/<name>/, plus one line in modules/index.ts (ARCHITECTURE §5):

  • service.ts holds the use cases. It calls repositories and domain rules, and after a successful write it publishes a domain event, such as checkin.recorded (FR-LIVE-01). Routes never publish.
  • A module reaches another only through that module's index.ts, or its events. ctx carries the rest: the repositories, the event bus, the clock, config, the adapters, the rate limits, shutdown and the LAN addresses. Tests build it with an in-memory database, a fixed clock and a fixed address.

  • screens/, components/, and api.ts with its query keys and hooks. Server state lives in TanStack Query.
  • A feature imports only shared/ and packages, and links to other features by URL. Only app/ knows every feature.
  • shared/live holds the tab's one EventSource and turns its events into batched refreshes (FR-LIVE-03).

The data stays in SQLite behind the repositories, with dates as ISO text, so a move to Postgres changes only packages/db (§6). The design system names its tokens by role, never by colour. Tests check every colour pair (NFR-USE-01) and fail on a literal colour, duration, z-index or opacity in component CSS (ARCHITECTURE §9).

7.2 Key algorithms

Each rule is written once, in packages/domain, and keeps its tests (ARCHITECTURE §7). Dates are YYYY-MM-DD in the gym's time zone, and the clock and the time zone are always passed in.

7.2.1 Weeks, pace and status

The terms are defined in §1.3; Today and the board show the results (FR-TODAY-01, FR-BOARD-01).

  1. A visit is a local day, in the gym's time zone, with at least one check-in. Several check-ins on one day count once.
  2. Day 0 is the joined date. Only visits on days 0 to 89, up to today, count. Week n holds days 7(n−1) to 7n−1, and week 13, cut short by the window, holds days 84 to 89.
  3. Week n is finished once today is day 7n or later, and week 13 once today is day 90. The week that holds today is in progress.
  4. Pace is the mean visits of the last 3 finished weeks, or of all of them while fewer have finished, to one decimal. There is none until week 1 finishes.
  5. Status takes the first rule that matches, over the finished weeks:
    1. slipping: 2 or more, and the last two each under 2 visits;
    2. new: fewer than 2;
    3. on the line: the last one had 3 or more visits;
    4. below the line: anything else.
  6. Today's four KPIs count the viewer's members in their first 90 days (FR-TODAY-01):
    • new members: how many there are;
    • the share on the line: the percent on the line among those with at least one finished week, or none when no one has one;
    • slipping: how many are slipping;
    • nudged this week: nudges sent in the last 7 days, the whole gym's for an owner, and the ones a coach sent for a coach.

For example, on day 20 a member has two finished weeks. With 4 visits in week 1 and 1 in week 2, they are below the line, at a pace of 2.5. With 1 visit in each, they are slipping.

7.2.2 Came back

  1. A nudge came back when the member has a check-in strictly after the nudge was recorded and no more than 7 days (7 × 24 hours) after it (FR-NUDGE-07). A check-in at the same instant doesn't count, and one at exactly 7 days does.
  2. The rule compares instants, so the gym's time zone doesn't change the answer.
  3. It is worked out from the check-ins each time it's shown, and never stored (§6.1).
  4. The nudges log shows the outcome (FR-NUDGE-06): "Came back"; otherwise "No visit yet" while the nudge is under 7 days old, and "No visit in 7 days" after that.
  5. Reports count how many of the last 90 days' nudges came back (§7.2.7).

7.2.3 Board order and "Slipping now" order

The board (FR-BOARD-01):

  1. It lists the viewer's members in their first 90 days: the whole gym for an owner, and their own members for a coach (FR-STAFF-07). Archived members are left out (§1.3).
  2. Slipping members come first.
  3. Within each group, the newest joiners come first, by joined date, then the lower id, so the order is stable.
  4. Today's board keeps this order, so its first slipping row, the one with "Nudge →", is its first row whenever anyone is slipping (FR-BOARD-02).

"Slipping now" on Today (FR-TODAY-02):

  1. It lists the slipping members of the same list.
  2. The viewer's own members come first: those they coach, so an owner who also coaches sees theirs at the top.
  3. Then the most days since the last visit come first. A member who never visited counts as one day more than their days since joining.
  4. Then the lower id.

7.2.4 The phone rule: the gym's country wins

  1. A trailing extension, such as "x12" or "ext. 12", is dropped, and the digits are kept. With no digits there is no phone.
  2. The digits are read in the gym's country, where a trunk 0, the country code and the country's own international prefix (011 in the US, 00 in the UK) all work. If they make a real number there, that is the answer, with or without a "+" (FR-GLOBAL-02, answers.md Q34).
  3. Otherwise a number without "+" is refused.
  4. A "+" number is read as international, and kept if it is a real number for its country code.
  5. Failing that, it is kept if its country isn't the gym's and its length is possible there, since the phone data can lag behind newly assigned numbers. The gym's own code is never kept on length alone.
  6. What is kept is stored as E.164. Only the server runs this rule, on libphonenumber's full metadata, for the kiosk, Add member, the member page and the import. The web only formats numbers (FR-MEMBER-03), and ESLint keeps the rule out of it.

7.2.5 The import's date order

  1. The values come from the file's date column: the join dates for members, or the check-in times for check-ins.
  2. A year-first date, such as 2026-03-04, reads one way only and settles nothing.
  3. In any other date, a first number over 12 can only be a day, so that date reads only day first. A second number over 12 means it reads only month first.
  4. If some dates read only one way and none only the other, the file settles the order. The line says "Set from the file: some of its dates only read this way."
  5. If no date settles it, or dates point both ways, the gym's country sets it: the order its locale writes dates in (FR-GLOBAL-03), such as month first in the US and day first in the UK. The line says "Set from your gym's country. Check the first rows below."
  6. The owner's flip, "Read them day first" or "Read them month first", wins over both. The first rows show as read in the order chosen, such as "Row 2: 03/04/2026 is 3 Apr 2026", or say they can't be read that way (FR-IMPORT-04).

7.2.6 Import matching and planning

The planner is pure. It returns what to create, update and skip, with problem codes that the API words from copy. The check step and the commit run the same plan, and only the commit writes (FR-IMPORT-08).

  1. Reading. The file is read as CSV, and its first non-blank line is the header. Rows keep their spreadsheet numbers, the header being row 1, so each "Row {n}: …" points at the right line (FR-IMPORT-05). A row with more or fewer columns than the header is reported.
  2. Mapping. Each field's column is suggested by matching the headers, in lower case with only letters and digits kept, against that field's common export names, in priority order. A column feeds one field at most, and the owner can change any choice. Without the required columns nothing is planned, and the page names what's missing (FR-IMPORT-02).
  3. A member row is read field by field: the name, splitting a "Full name" (FR-IMPORT-03); the join date, in the date order (§7.2.5); the phone, by the phone rule (§7.2.4); the email; and the coach, matched by email to the gym's staff. A row with no name, or no readable join date, is skipped. A bad phone or email is left blank, and an unknown coach leaves no coach, each with a note (FR-IMPORT-05).
  4. Matching. The row is matched to the gym's members, archived ones included: by external ID first, then by phone (FR-IMPORT-06).
  5. A matched row is skipped when an earlier row matched the same member, or when it would give them an ID an earlier row used. Otherwise it updates only the fields that differ, and a blank never overwrites. With nothing to change, it is skipped as up to date. A phone that is another member's is left as it was, with a note. An archived member is restored, and the row says so (FR-IMPORT-09).
  6. An unmatched row is skipped when its external ID or phone came earlier in the file. Otherwise it creates a member.
  7. A check-in row finds its member by ID, then by phone, read by the phone rule. It is skipped when no member matches, when its time can't be read in the gym's time zone and date order, or when the time is in the future, on a day before the member joined, or within an hour of another of that member's check-ins, stored or earlier in the file (FR-IMPORT-07).
  8. The commit plans again inside one write transaction, against the gym's data as it is then, so a kiosk check-in made in the meantime counts for the hour rule. It writes the creates, updates and check-ins together, or nothing on a clash. A row's coach and a check-in's member must belong to the gym (FR-IMPORT-08).
  9. The result shows what was created, updated and skipped, and open screens refresh once (FR-IMPORT-10, FR-LIVE-03). The check step for 2,000 rows shows in under 5 s (NFR-PERF-04).

7.2.7 Report cohorts and the visits-by-week chart

Reports count every member who hasn't been deleted, archived ones included (FR-REPORT-01). Visits are days in the gym's time zone (FR-REPORT-03).

Cohorts:

  1. The rows are the gym's current month and the three before it, oldest first. Each holds the members who joined that month.
  2. For day N, which is 30, 60 or 90, a row takes its members who are at least N days in.
  3. Its figure is the percent of them who visited in the week before day N, days N−7 to N−1, as a whole number. With no member that far in, there is no figure.

For example, a member who joined on 1 August counts toward day 30 from 31 August, and is still coming if they visited between 24 and 30 August.

Visits by week:

  1. For each of weeks 1 to 13, the chart takes every member whose week has finished.
  2. It splits them by their last visit: still coming if it was in the last 14 days, today included, and slipped otherwise, which includes members who never visited.
  3. Each line's point is its group's mean visits that week, to one decimal. An empty group has no point.
  4. The line at 3 visits a week is drawn with them (FR-REPORT-02).

The nudge figures count the nudges sent in the last 90 days, by the gym's day and up to now; how many came back (§7.2.2); and the rate, as a whole percent, or none when nothing was sent.

10. Acceptance tests

The first version is accepted when every Must in §3 passes these tests on Chrome and on Safari, through Playwright's WebKit (NFR-COMP-01), the §4 checks below pass, and the checks in §10.15 have been made by a person. Each automated test's name starts with the ID it covers (NFR-MAINT-03), so one row here can be several tests.

How the tests run:

  • npm run e2e runs the 13 Playwright flows, one file each in apps/e2e/src. The projects are Chrome desktop and phone, through the installed Chrome, and WebKit desktop and iPhone, standing in for Safari. The kiosk flow runs on an iPad and on the two phone projects, so it runs in both engines too.
  • Each engine has its own stall-mode server, with a freshly seeded demo gym in America/Chicago, so the gym is in the US (FR-GLOBAL-05). Demo logins come from the seed module, never typed into a test. A test-only factor lifts the rate limits, so the limits themselves are checked by API tests.
  • Flows run in parallel against the same server. A flow that changes data uses a gym it signs up, or members and staff it adds, so flows don't meet. A step done "through the API" calls the API directly, as the signed-in user.
  • A speed check times from the navigation until the screen's data shows, not just its title.
  • API tests run in npm test, against an in-memory database with a fixed clock. Their paths are under apps/api/src; other paths are given in full.
  • In "Expected result", "1:" answers step 1.
